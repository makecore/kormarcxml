# ISO 2709 conversion and equivalence

`decode_record(bytes, encoding=None, *, errors="strict", recover=False, issues=None)`
parses one record. `iter_iso2709(binary_stream, ..., max_record_length=99999)` reads
one length-framed record at a time; it handles short reads and never loads an
entire collection. `encode_record(record, encoding=None, *, errors="strict")`
returns one binary record. Stream inputs and outputs are binary, including stdin.

The supported directory layout has three-byte tags, four-byte field lengths,
five-byte offsets, two one-byte indicators, and one-byte subfield codes, expressed
by Leader/10–11 `22` and Leader/20–23 `4500`. Other ISO 2709 layouts fail explicitly.
The leader is exactly 24 ASCII characters. Tags are three ASCII digits; indicators
are one printable ASCII character (including blank); subfield codes are one
printable nonblank ASCII character. Whether such a tag or code is valid KORMARC
is a separate validator concern. Unknown and local 9XX fields remain intact.

The parser checks the directory terminator (0x1E), field terminators (0x1E), record
terminator (0x1D), subfield delimiters (0x1F), directory numeric entries, field bounds,
and complete nonoverlapping field coverage. It rejects unlabelled bytes before a
first subfield, embedded reserved delimiters, and unreferenced payload bytes,
because the logical model cannot preserve them safely. Recovery does not invent
missing delimiters, guess record boundaries, or silently skip damaged records.

`recover=True` permits one recoverable structural deviation: directory order
may differ from physical field order. Fields are returned in **directory order**;
serialization rebuilds payload in that order. Supply `issues=[]` to collect the
`iso.directory_order` warning; otherwise a Python warning is emitted. Parseable
semantic errors, such as repeated nonrepeatable fields, are retained regardless
of this option and can subsequently be reported by the validator.

Limits are 99,999 bytes per record and 9,999 bytes per field **including** its field
terminator. The binary encoder rejects overflow instead of truncating decimal
positions. Large collections can be streamed but an individual record beyond the
ISO 2709 width limit must remain XML or use another representation.

## What a round trip preserves

The logical model preserves the leader, control-field strings, indicator strings,
subfield codes/strings, field/subfield order, and repetitions. On encoding,
Leader/00–04 (record length), Leader/12–16 (base address), directory field lengths
and offsets are **recomputed from encoded bytes**. Directory and terminators are
therefore represented structurally rather than as extra XML text elements.

| Check | Meaning |
|---|---|
| Structural equivalence | Same field kinds, tags, indicators and ordered subfield structure |
| Bibliographic equivalence | Exact stored strings, with no attempted semantic normalization |
| Code-point equivalence | Exact Unicode code-point sequences, including combining characters |
| Fixed fields | Exact fixed-field text and nonsynthetic leader positions |
| Byte equality | Possible only under the additional conditions below |

Byte equality requires an originally consistent supported directory layout,
physical field order matching directory order, unchanged leader encoding intent,
the same explicit byte codec where necessary, lossless decoding/encoding, and a
canonical byte representation for that codec. It is demonstrated for the supplied
UTF-8 and EUC-KR fixtures, not promised for every legacy byte sequence. Recovery,
character replacement, transcoding, normalization by external software, or a
noncanonical legacy encoding can break byte equality even when logical content is
retained. Invalid records may fail parsing instead of having a round-trip claim.

## XML transport

`record_to_xml(record)` serializes one record; `write_xml(records, binary_stream)`
streams a collection. `iter_xml(binary_stream, max_record_bytes=10485760)` reads
records from either a standalone record or collection. The namespace is the
existing `http://www.loc.gov/MARC21/slim`; KORMARC semantics remain a separate
profile. A record contains one leader then arbitrarily ordered `controlfield` and
`datafield` elements; data fields contain ordered `subfield` elements. Attribute
values carry tags, indicators and subfield codes. A blank indicator is literally
one space, not `#` or a missing attribute.

The independently authored bundled XSD permits interleaved control/data fields so
that unusual input ordering is retained. It is **not** the LC XSD; consumers that
require LC's control-fields-before-data-fields order must validate against the LC
schema separately and decide explicitly how to handle such records.

DTD declarations, external entities, unexpected structure and unsupported
record-level attributes are rejected. XML comments and processing instructions
are presentation metadata and not part of the preserved MARC model. The default
10 MiB read-window limit bounds an individual record and excessive material
between records; it is a conservative resource limit, not an exact serialized
record-size accounting API. XML parser native depth/text limits also apply.
`schema_validate(source)` accepts XML bytes/text or a binary stream and validates
at most 10 MiB as one document; for larger collections validate one record at a time.

The dataclasses have frozen attribute bindings but their field/subfield lists are
ordinary mutable lists. Copy-returning `.add_field`, `.remove_fields` and
`.replace_field` helpers support predictable edits; these objects are **not**
deeply immutable. Avoid sharing mutable lists across concurrently editing callers.
