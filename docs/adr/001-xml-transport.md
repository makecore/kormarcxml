# ADR 001: MARCXML vocabulary as transport, KORMARC as explicit profile

Status: accepted for the initial implementation. Date: 2026-09-16.

KORMARCXML is an independent open-source framework, not an NLK or KS standard.
The XML namespace does not identify which cataloguing semantics a record follows.

## Decision

Use the established `http://www.loc.gov/MARC21/slim` vocabulary for the XML bus
(`collection`, `record`, `leader`, `controlfield`, `datafield`, `subfield`).
Select KORMARC semantics through the validator's versioned profile. Do not invent
an `nl.go.kr` namespace, silently apply MARC 21 content rules, or add a separate
XML element for every KORMARC field.

This is approach A at the vocabulary/transport level. The bundled XSD is an
independently authored structural schema, **not a verbatim copy of, or a claim of
identity with, the LC XSD**. It permits field-order preservation, including
interleaved control/data fields accepted by the core. Therefore passing our XSD
must not be reported as passing the official LC XSD. An application requiring
strict LC schema conformance must validate against an independently acquired LC
schema as a separate gate; it must never reorder data silently to obtain a pass.

## Evidence and limits

The [LC design page](https://www.loc.gov/standards/marcxml/marcxml-design.html)
describes a generic schema and a separate validation mechanism; its official
search-index excerpts were available, but direct page retrieval returned HTTP 403
during this investigation. The [OAI implementation guideline](https://www.openarchives.org/OAI/2.0/guidelines-marcxml.htm)
was directly read: it supplies the namespace, schema reference, and an instance
with blank indicators and repeated fields. The [ABES IdRef developer documentation](https://documentation.abes.fr/aideidref/helpdeveloper/ch03s02.html)
was also directly read and explicitly uses MARCXML syntax for UNIMARC authority
records. This is operational precedent for sharing syntax without sharing MARC
21 field semantics; it is not an official endorsement of a KORMARC profile.

## Alternatives

| Criterion | A: existing vocabulary + profile | B: project-owned namespace + generic schema |
|---|---|---|
| Interoperability | Existing XPath and MARC XML readers can read the vocabulary | Namespace-aware consumers need an adapter |
| Standards semantics | Requires explicit warning that KORMARC is not MARC 21 | Profile identity is more visible, but namespace alone still cannot specify all rules |
| Namespace ownership | Reuses an existing identifier without claiming ownership | Must establish durable project-controlled URI and governance |
| XML tools | Existing parsers, editors and selectors can be used | Standard XML tools work; existing MARC selectors need changes |
| MARCXML compatibility | Vocabulary-level compatibility; separate official-schema gate needed | Requires namespace conversion and a conformance gate |
| Maintenance | Semantic changes live in versioned rules | Must maintain schema, namespace policy and adapters |
| Versioning | Software version and rule-profile version evolve separately | Also needs namespace-version and migration policy |
| KORMARC changes | New fields need rules, not new XML element definitions | Same advantage if generic structure is retained |
| Authority / holdings | Reuse core with separately verified profiles | Reuse base schema with additional profiles |
| User expectations | Documentation must prevent MARC 21 semantic inference | New official-looking name risks implying NLK/KS endorsement |
| Future standardization | Migration to an officially governed namespace remains possible | Project namespace may conflict with a future official choice |

## Consequences

The application must retain profile identity outside the canonical MARCXML
record, for example in job configuration and validation reports. A receiving
system must be told `KORMARC bibliographic / KS X 6006-0:2023`; it must not infer
this from the namespace or run LC semantic stylesheets without a reviewed
crosswalk. API calls and examples use the KORMARC profile explicitly/defaultedly
within this KORMARC-specific package; cross-format integrations must set it.

Preserve ordered lists, blank indicators, repeated subfields and exact Unicode
code points. Directory offsets and byte lengths are regenerated by the ISO 2709
writer. Byte-identical preservation is a narrower property, tested only for
canonical, valid inputs with the same encoding. XML 1.0 cannot represent every
possible byte or control character; rejection is preferable to silent loss.

Revisit the decision if an official KORMARC XML namespace is established, or a
consumer demonstrably needs additional canonical content that cannot be carried
in the generic vocabulary. Until then, custom provenance and validation reports
remain separate artifacts rather than unsolicited MARC namespace extensions.
